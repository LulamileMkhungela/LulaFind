# Every journey, and what happens when the data is not there

The question this answers: **does the app validate what it needs before it moves you on, and is every journey finished end to end or clearly parked?**

Two rules, applied screen by screen:

1. **A required field is checked before the next step, and the message names the field.**
   Nothing advances on half a form, and no screen says "something went wrong".
2. **A tap always answers.** Either it moves, or it says why it cannot and how to get past it
   (sign in, follow each other, join a Spotlight). A disabled button with no explanation is
   not allowed to be the answer.
3. **A journey can be left and finished later.** Whatever was typed is kept, and the screen
   says so — with one tap to throw it away and start fresh.

Generated by `tools/e2e-journeys.mjs`, which drives a real Chromium (153.0.8010.0) against the
running app, creates **two real accounts through the real sign-up screen**, and reads its
verdicts back from the app's own store. Screenshots: `docs/e2e-journeys/`.

## Honesty notes (what this run is not)

- The run forces `?demo=0&data=local`. `?data=local` is a **development switch**: it puts the
  app's real services, screens and validation on top of a local store on the device instead of
  the hosted project. The hosted Supabase project is not reachable from this container, so a
  browser test cannot sign in to it. Everything else — screens, validation, services, the store
  the app reads — is the real code path.
- Nothing is seeded: both accounts are created through the five-step sign-up screen inside the run.
- The one thing simulated by hand is time (a lookout aged past its 24 hours), because a browser
  test cannot wait a day. That is the lookout run, `tools/e2e-lookout.mjs`.

### The safety journeys (see `docs/E2E-LOOKOUT.md`)

Sign up → allow the app to post a case about me → start a lookout with location → a follower sees
the last seen → 24 h later the follower is asked "are they okay?" → one "no" flags them and the app
publishes a possible-missing-person case → the person says "I'm here" and the case is deleted →
with the setting off the same "no" posts nothing. 16 steps, 0 problems, 0 console errors.

## What the app does when a journey cannot be finished

- **A screen is not a dead end.** The Safety centre, New post and Story all offer the way on, and a
  removed post says "This post is no longer available" with a way home instead of an empty screen.
- **A gate names the gate.** Commenting, reacting, chatting and reporting say "Sign in" rather than
  swallowing the tap; chat says which follow each side still needs.
- **Nothing pretends.** If a build has no camera module, the screen says so and opens the photos
  instead of showing a dead button.

## Not clicked through in a browser (audio, device, or admin-only)

Listed so nothing here reads as more than it is:

- **Android device flows** — camera capture, share sheet, push notifications, geolocation in the
  native shell. The web fallbacks are what the browser run exercises; the APK needs a rebuild to
  retest on a phone (`npx cap sync android` is done; the build needs an Android SDK).
- **Real-time messaging between two devices** — the hosted backend is unreachable here, so chat is
  exercised on the local store only.
- **Admin-only actions** — remove post, suspend a person, delete an account. The screen and its
  gate are verified; the actions need an admin account that cannot be created here.
- **Cron** — `lula_lookout_ask_due()` in `supabase/schema.sql` is written but never executed
  (`psql` is not installed in this container), so the 24-hour ask is verified by driving the app's
  own `runDue()` path, not by a scheduler.
